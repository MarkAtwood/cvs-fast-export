= Go translation plan

The cvs-fast-export codebase is complex to the point of near
unmaintainability, and prone to flaky bugs from heap corruption
and stack-smashing.  One way to address this would be to translate it
to Go, which has similar syntax and types but handles dynamic
allocation more gracefully.

Helpfully, we on't have too write most of the first stage, because
this exists: https://github.com/arran4/golang-rcs

For branch/tag collation and changeset edge cases, see
link:cvs-collation-spec.adoc[CVS Collation and Symbol Resolution Spec].

This Golang library offers lossless deserialization of an RCS master into
the following structures:

----
type Lock struct {
	User     string
	Revision string
	Strict   bool
}

type RevisionHead struct {
	Revision     string
	Date         time.Time
	Author       string
	State        string
	Branches     []string
	NextRevision string
	CommitID     string
}

type RevisionContent struct {
	Revision string
	Log      string
	Text     string
}

type File struct {
	Head             string
	Branch           string
	Description      string
	Comment          string
	Access           bool
	Symbols          bool
	AccessUsers      []string
	SymbolMap        map[string]string
	Locks            []*Lock
	Strict           bool
	Integrity        string
	Expand           string
	RevisionHeads    []*RevisionHead
	RevisionContents []*RevisionContent
----

----
  Below is how tags are handled in the current Go version, based on the implementation in cmd/cvs-
  fast-export/monolith.go. This is descriptive (not normative), so you can decide what behavior to
  keep/change.

  Where tag data comes from

  - Tags are read from the RCS symbol table per file during BuildMaster.
  - SetRefs assigns symbol names to branch heads and also records tag targets as []Tag (name + commit
    pointer).
  - collectTags merges per‑file tag targets into Repo.TagTargets[name] and keeps a deterministic
    TagOrder.

  How tags are emitted

  - Tags are emitted in Emitter.EmitRepo.
  - For each commit, after applying file ops, the emitter checks tags in tagNames order and emits:

    reset refs/tags/<tag>
    from :<current commit mark>
  - This happens when tagMatchesState(tagTargets, state) returns true.

  What tagMatchesState does

  - Builds a set of target paths from the tag target list.
  - Requires that the current tree state has no extra files not in the target set.

Examining some of the remaining failures, like deadbranch,v, they look
like results of the C and Go versiuns choosing to omit commits in a
different order.  Compare the codebases and try to work out what
the differences are.

----
  Here are the concrete C vs Go differences that explain “omit commits in a different order,” with
  pointers to the code.

  1) C never skips commits with zero fileops; Go does.

  - C exporter (export.c:export_commit) always emits a commit, even if the merge-join produces zero
    operations. There’s no “skip empty commit” guard in export.c.
  - Go exporter (cmd/cvs-fast-export/monolith.go around EmitRepo) explicitly skips commits when
    len(ops)==0 once the branch has seen live content:
      - if len(ops) == 0 && liveSeen[c.RefName] { ... continue }
        This is the most likely source of “omit commits in a different order,” because once you
        drop a commit, all subsequent commits shift and the parent chain still refers to the latest
        emitted commit.

  2) Dead, unnamed branches are discarded earlier (and warned) in C; Go only drops the head.

  - C (revcvs.c around line ~603) detects an unnamed head whose entire chain is dead and untagged,
    warns, and marks the head for discard:
      - warn("discarding dead untagged branch %s in %s\n", ...)
  - Go (fixUnnamedHeads / discardZeroHeads in cmd/cvs-fast-export/monolith.go) sets h.Number = Zero
    and removes the head, but doesn’t emit the warning and doesn’t explicitly prune commits. Those
    commits can still be reached via branch collation and then later get filtered by the “skip no-
    op commit” logic. That changes the omission order relative to C.

  3) Commit ordering differs before emission.

  - C canonicalizes a global commit list (export.c:canonicalize) with a topological shuffle that
    tries to match git-fast-export order.
  - Go’s Build() sorts commits mostly by date/file key inside a branch and then links parents in
    that order. That means “which commit would have been omitted next” can differ, especially once
    you start skipping empty commits.

  If you want to align the omission order with C, you basically have two levers:

  1. Remove or constrain Go’s empty-commit skip so it matches C (emit all commits, even no-op).
  2. Ensure dead-branch pruning happens at the same stage as C (discard entire branch earlier, not
     just its head).

  If you want, I can sketch a minimal change to mirror C’s behavior (likely: emit commits
  unconditionally, but keep the dead-branch discard + warning), then
  we can test what breaks next.
